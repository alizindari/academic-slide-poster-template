Start with the first stage, before assuming the audience knows what fine-tuning means. A large language model is first trained on a very large collection of text, such as books, websites and articles across many topics. It learns language patterns and general knowledge by learning to predict text. Training a large model from scratch takes substantial computation and time. The result is a general base, not yet tailored to our particular application. It can already have useful code or domain knowledge; general does not mean it has none. End with the reason to reuse it: do this expensive base training once, then use the same base for many downstream tasks. Here, once means sharing the cost of one base model across applications, not a claim that models can never be trained further or that all training pipelines have only one pre-training run. The diagrams and cost descriptions are qualitative. Next, reuse this exact base model and explain fine-tuning separately. Sources: DISeL, Introduction and §2; LoRA vs. Full Fine-Tuning, Introduction; Devlin et al. (2019), BERT §3.

Fine-tuning means continuing to train a pre-trained model on data for a particular task. Begin with the same general model from the preceding slide; we reuse its learned weights instead of starting over. Add a much smaller dataset focused on the target task. For example, code data can help the model become better at writing code. The matching network drawings represent the same architecture before and after training, with highlighted edges only illustrating a change, not a claim that just a few weights move. Reveal the benefit last: training a new large model from scratch for each application would repeat the expensive work from the previous slide. Reusing the base usually needs much less data and compute to learn the task. The comparison is qualitative, not a speed ratio or a claim that every fine-tuning run is cheap, and not a claim that every use of a language model requires fine-tuning. We focus on supervised fine-tuning in this talk. Explain the count before the formula. Each masked position is one prediction question, so the first sample supplies two scored tokens and the second supplies one. N is three, not two samples, the vocabulary size, or all visible tokens. Flatten the evaluated positions across all samples into indices i=1,...,N. For each position p_i is the model probability assigned to the original correct token, conditioned on the corrupted input. The words and probabilities shown are invented for this illustration; assume each answer is one token. They are not measured model outputs or source-dataset records. Using natural logarithms, add -log(0.5), -log(0.25), and -log(0.125), divide by three, then exponentiate: the result is four. For a larger test set, sum token losses and counts across batches, excluding padding and unscored positions, then exponentiate the total loss divided by N. This is token-weighted aggregation, not an average of sample perplexities. Higher probabilities for the correct tokens produce lower loss and lower perplexity. Three practical limitations, based on the overhead paragraph in §3 (page 4) and the limitations paragraph in §8 (page 9) of the supplied DISeL paper. First, each adapted matrix adds W_g with r d_x entries and b with r entries, or r(d_x + 1) parameters beyond LoRA at the same rank and with the same target modules. These parameters also need gradients and optimizer state during training, and the gate branch adds activations. For a square 4096-by-4096 projection at rank 16, DISeL has 196,624 trainable parameters versus LoRA's 131,072, about 1.5 times the adapter parameter count. This is not a 1.5-times total-memory or runtime claim; the frozen model still occupies memory. Second, computing gates costs O(r d_x) arithmetic per token and adapted matrix, plus sigmoid and elementwise scaling. Because G(x) depends on the input, A G(x) B cannot generally be merged into one fixed weight matrix as a standard LoRA update can. This is a structural inference cost, not a measured latency percentage; the paper does not provide a timing or peak-memory benchmark. Soft gates near zero do not by themselves skip the adapter computation. Third, retention is empirical, not guaranteed for every earlier capability. Results depend on gate initialization, learning rates, and the adapted modules. Without pre-training data in the fine-tuning loss, suppression of updates on earlier inputs is not directly enforced. The reported experiments concern single-task fine-tuning; multi-task and continual learning remain future work.
